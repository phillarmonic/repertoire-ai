## v1.12.0: the lockfile release

Repertoire installs a skill into every coding agent you use, then pins it with a
lockfile you commit. This is the first release described that way, and the reason
is on the lockfile page: an update that would overwrite a copy you edited by hand
stops and names the path instead.

Install on macOS, Linux or Windows:

```bash
curl -fsSL https://raw.githubusercontent.com/phillarmonic/repertoire-ai/master/install.sh | bash
```

Every asset ships with `checksums.txt`, and the installer verifies the digest
before it moves the binary into place.

### Added

- **A concept page for the lockfile**, which says what the digest covers, what a
  refusal looks like, and what a digest cannot prove:
  https://phillarmonic.github.io/repertoire-ai/concepts/lockfile/

- **A comparison against copy-paste**, including the row where copying wins:
  https://phillarmonic.github.io/repertoire-ai/vs-copy-paste/

- **Slash-only skills install as OpenCode commands.** A skill whose frontmatter
  declares `disable-model-invocation: true` is offered to the model like any
  other when it sits in the skills directory, because OpenCode keeps its
  user-invoked entries in `command/` instead. Such a skill is now written there
  too, with `argument-hint` mapped to `$ARGUMENTS`.

- **Comma-separated names** in `install`, `update`, `remove`, `show`,
  `stub list`, `stub get`, `catalog update` and `catalog remove`, so
  `repertoire catalog update phillarmonic,andy` updates two catalogs.

### Fixed

- `argument-hint: [target]` and a quoted flag no longer read as invalid
  frontmatter, which failed the whole skill.

- A global install for the `opencode` target follows `XDG_CONFIG_HOME` instead
  of writing to `~/.config/opencode/skills` on a machine where OpenCode never
  reads that directory.
